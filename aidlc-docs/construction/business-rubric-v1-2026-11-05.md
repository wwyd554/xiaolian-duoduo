# 销练多多业务评分与专项复练 v1 实施记录

日期：2026-11-05。实现标识：`rubricId = xiaolian-sales-core`，`rubricVersion = 1.0.0`。

代码已接入，并完成自动化、真实模型和浏览器验收。本记录以当前源代码为准，不以研究方案或开源项目的功能宣称代替已实现能力。

## 一、本次完成的范围

1. 新陪练报告采用固定业务考点，模型判断单项行为，程序计算总分。
2. 聊天记录、录音转写导入复盘共用同一套业务评分规则；原有导入总结、发现及回复建议继续保留。
3. 原话证据校验到消息 ID、说话人和完整原句；评分状态区分未做到、不适用和证据不足。
4. 复盘页面展示单项依据、一个主要改进动作、风险待核实项，以及定位原话操作。
5. 已评的弱项可创建专项再练，沿用原场景及评分规则快照，并在新报告比较同一考点的前后表现。
6. 历史旧报告保持兼容，不自动重算或冒充新版规则报告。

未在本次实现：企业规则审批、人工改分与申诉、班级任务、合格线校准、正式认证、跨行业法规库、企业产品知识库管理、长期成长曲线。导入复盘暂无自动创建对应陪练场景的功能。

## 二、评分规则与产品事实分开

规则实现：`server/app/services/business_review.py`。

| 考点 | 默认权重 | 判断重点 |
|---|---:|---|
| S1 建立沟通与确认议程 | 10 | 来意、是否方便、交流重点 |
| S2 探索并核对需求 | 30 | 问题、影响/优先级、客户确认 |
| S3 将价值与需求对应 | 25 | 价值解释关联需求、已知条件和未知边界、客户回应 |
| S4 理解并回应异议 | 20 | 异议机会、澄清原因、回应及确认 |
| S5 对齐下一步 | 15 | 动作、负责人、时间；明确拒绝时尊重结束 |

各项只取 0 / 1 / 2，分别表示未做到、部分做到、完整做到；每一项有固定中文行为锚点。模型不得输出或修改权重、总分和考点集合。

**S3 的实施口径：** 没有产品资料不等于销售表达不合格。销售能够对应客户需求解释价值、说明已知条件和待核实边界，并获得客户回应，可评为 2 分。模型不能为拿高分编造效果、价格或案例。`productFactsVerified=false` 时，产品事实及承诺授权仍显示未核实，不得把行为得分解释为事实审查通过。

总分由程序按适用项归一化：

`totalScore = round_half_up(100 × Σ(weight × score / 2) / Σ适用 weight)`

所有适用项必须已评才生成总分。零分是有效结果；未完成评估是 `null`，不是零分或默认及格。`passThreshold` 固定为 `null`，没有 60/80 分达标线。

## 三、证据与失败处理

模型逐项返回：考点、状态、分数、判定理由、原话证据、检查消息范围、缺失动作、下一步练习。服务端根据规则快照补齐标签和权重。

- 考点必须与快照完全一致，不能缺项、重复或凭空增加。
- 引用必须来自本次对话：`messageId` 存在、`speaker` 对应原角色、`quote` 为完整原句或完整消息。截掉否定词、只摘关键词、错引用其他消息均被拒绝。
- 正分必须有销售发言；S2/S3/S4/S5 的 2 分还必须有客户回应证据。客户说了需求不等于销售完成了需求确认。
- 0 分必须声明核查整份对话。没有发生的动作允许没有对应原话，但不能生成不存在的引用。
- S4 评分必须引用客户异议并标记机会已出现。仅当 `objectionRequired=false`、核查全对话且没有异议机会时，S4 可不适用。其他必考项不能因为找不到证据而被删出分母。
- 缺少双方有效发言、资料被配置为不完整，或超过完整核查限制时，返回 `incomplete`，各项为证据不足且总分为 `null`。当前上限为 250 条有效消息、60,000 字符；导入接口另有 200 条、30,000 字限制。
- 模型调用失败、结构错误或证据校验失败会抛出错误，交由持久任务队列按既有有限重试策略处理；耗尽后显示失败并可手动重试，不写一份默认分数报告。

原话校验能够证明引用存在及角色一致，不能单独证明模型对语义的判断正确；仍需人工对照样本校准。

“对话完整”默认是场景配置假设，不是系统自动检测录音缺失的结论。录音转写仍需用户核对角色和内容；当前导入界面未增加完整性开关。

## 四、风险提示的边界

风险项分为产品事实、未授权承诺、客户边界三类，均需原话证据。客户边界问题还需同时有客户的拒绝表达。记录状态为 `pending_review`。

有风险项时 `riskChecks.status = review_required`；没有列出风险时仍是 `not_checked`，不显示“合规通过”或“无违规”。即使提供产品资料，也只表示可以对照本场资料，不能自动视为行业合规认证。

本版尚无人工审核队列、确认/排除接口或改分审计。不能把界面中的“待核实”解释为人工已经处理。

## 五、冻结规则与专项再练

`PracticeState` 新增 `rubricSnapshot` 和 `practiceFocus`，存储在现有 `session_states.state_json`，无需新增数据库表。新建会话立即冻结规则；旧会话首次生成新版报告时补快照并保存，后续重试沿用该版本。

专项再练流程：

1. 用户在报告选择“专项再练”或某个考点的“练习这一项”。
2. 服务端只接受本人已结束、已有新版报告、确实已评为 0/1 分的考点。无法评估的项不能伪装成弱项；全部完整做到时不自动制造改进项。
3. 服务端读取原会话场景快照和评分快照。源场景快照缺失、版本不支持、同版本权重/锚点不一致均返回 409，不能回退到已编辑的新题。
4. 前端用返回的 `scenarioSnapshot` 展示客户、说明、开场与目标，创建新会话时仅传来源会话和考点 ID。
5. 后端重新校验来源权限及场景，冻结原场景和完整考点集合；焦点影响练习方向，不悄悄改变评分分母。
6. NPC 获得服务端固定的客户行为提示，保持原客户事实和角色；不会收到上次分数，也不会执行报告中模型生成的任意指令。正常运行时与回退对话链路均已接入。
7. 新复盘从原报告读取真实旧分；仅规则快照相同、相应考点两次均已评时，输出分数变化。否则显示不可比原因，不编造提升幅度。

再练是重开同题并强调一个能力，并非从任意历史话术处回放、也不自动复制旧消息。原场景目标仍保留；没有新增一套独立的专项过关机制。

## 六、接口与返回契约

| 接口 | 本次变化 |
|---|---|
| `POST /scenarios`、`PUT /scenarios/{id}` | 持久化并校验 `rubricConfig`；不支持的字段或非法值返回 400，仍按原有场景写权限控制 |
| `POST /sessions` | 可选成对字段 `practiceSourceSessionId`、`practiceCriterionId`；已有会话不能更换复练身份 |
| `POST /sessions/{id}/practice-plan` | 无 body 或 `{criterionId: "S4"}`；返回场景 ID、来源、焦点、固定练习指引、旧分、规则版本及 `scenarioSnapshot` |
| `GET /sessions/{id}/practice-state` | 返回 `rubricSnapshot`、`practiceFocus`，仍不暴露用户 ID 与整个原场景 |
| `GET /sessions/{id}/analysis-results` | 新报告顶层含 `businessReview`、`rubricSnapshot`、`practiceComparison` |
| `GET /sessions/{id}/feedback` | 附带 `businessReview`、`practiceComparison`；保留旧反馈字段 |
| `POST /reviews/import` | 导入时冻结默认规则，沿用现有异步复盘队列 |
| `GET /reviews/{id}` | `report.businessReview` 与 `report.rubricSnapshot`；消息带可定位的 `messageId` |
| `GET /reviews`、`GET /sessions` | 新分数保留 `null`，不替缺失旧子项生成零分 |

核心业务报告字段：

- `rubricId / rubricVersion / status / totalScore`。
- `criteria[]`：`id / label / weight / status / score / reason / evidence / checkedMessageIds / missingBehavior / nextPractice`。
- `coaching`：`keep / fix / nextPractice / focusCriterionId`。
- `coverage`：已评项数与适用项数。
- `riskChecks`：状态、局限说明及待核实项。

当前单项实际输出状态为 `assessed / not_applicable / insufficient_evidence`。前端兼容类型另保留 `evaluation_error`，但模型/校验失败目前通过整份任务失败状态表达，不能声称逐项失败重试已经实现。

## 七、配置与版本管理

评分配置从场景文档的 `rubricConfig` 读取，缺省评 S1–S5；前端尚无可视化规则编辑器。配置结构：

```json
{
  "rubricConfig": {
    "criterionIds": ["S2", "S4", "S5"],
    "objectionRequired": true,
    "productFacts": [],
    "productFactsVerified": false,
    "transcriptComplete": true
  }
}
```

- `criterionIds` 必须是 S1–S5 的非空且不重复子集；单项练习的评分范围应提前配置，不由模型看到表现后选择。
- `objectionRequired=true` 时，S4 不允许通过未出现异议被排除；缺机会需要显示证据不足。
- `productFacts` 最多 30 条，每条最多 2,000 字符；`productFactsVerified=true` 只有提供非空事实列表才生效。该标记是配置声明，不代表系统已经完成企业审批或外部事实验证。
- `transcriptComplete=false` 会阻止完整评分；不能以局部对话冒充完整证据。
- 权重与锚点为服务端版本内常量，当前不支持任意客户端自定义权重。同一版本不能改内容后继续沿用旧报告进行比较。
- 发布新规则需新增/更新版本并明确历史兼容策略；当前仅支持 `1.0.0` 的评估和专项复练，未知版本被拒绝，不静默升级。

场景创建、更新及批量导入已接入 `rubricConfig` 的持久化和校验。空对象恢复默认考点；不支持的配置字段（包括客户端覆盖权重或锚点）会被拒绝。批量导入中的无效配置记录为该场景的导入错误，不写入该条场景。已有会话仍使用已冻结的规则，编辑题库只影响后续新会话。

## 八、兼容和后续工作

- 新练习报告从业务结果生成少量兼容字段：`feedback.scores.overall` 和优点/改进/建议。不会伪造旧版 12 维和 9 子项评分。
- 有 `businessReview` 时前端走新版组件；老缓存报告仍走旧展示，不自动迁移，旧分数不与新版分数直接比较。
- 导入复盘评分一致，但没有原陪练场景，因此不展示或提供无效的一键专项再练。
- 目标完成状态与行为评分分开；本次没有以业务总分自动结束会话、判定成交或正式上岗。
- 下一步业务验收需真实标注样本、分项一致性、证据准确性、风险漏检检查；模型返回合法 JSON 不等于评分已满足业务验收。
