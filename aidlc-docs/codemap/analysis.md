## 项目定位与边界

这是一个面向销售的情境模拟训练产品：用户选择客户场景，通过文字或麦克风与 AI 买方对话，观察情绪、信任和谈判进度，并在结束后获得复盘。

## 一轮对话如何执行

1. `ConversationPage` 收集输入；麦克风通过 `/ws/transcribe` 上传 PCM16/16kHz/单声道，后端使用本地 faster-whisper 分段识别。
2. `ApiService` 带登录凭据请求 `/sessions/{id}/messages`。后端检查会话所有权，通过 `services/conversation.py` 进入默认开启的 Harness Runtime。
3. 从 SQLite 恢复场景快照、轮次、指标、目标和有来源事实。按预算组装上下文，为 NPC 和评估器提供不同视图。
4. NPC 回复与实时情绪评分并行。NPC 可选择四种受控工具，最多两次工具往返；评分只更新三个 1–10 指标、建议、表情和动作。
5. 收到 NPC 回复后，独立目标评估器检查目标 ID、完整原句、说话者和置信度。目标达成需有销售与客户双方证据，置信度至少 0.85；没有显式必需目标时，不推断自动结束。
6. 模型调用完成后才获取数据库写锁，再核对轮次、revision 和结束状态。成功时将消息、状态和暂存事实一起落库；并发旧结果不会静默覆盖新状态。
7. 前端播放 TTS 音频并驱动 VRM。若达到必需目标或轮数上限，服务端结束会话并入队复盘；用户也可手动结束。
8. Worker 在事务外生成报告，通过有效租约令牌提交结果。`ResultPage` 查询分析状态，读取报告并支持失败重试。

文本回路：工作台 → 会话 API → 状态/上下文 → NPC 与评分 → 目标核验 → SQLite → 工作台。
复盘回路：完成会话与入队同事务 → Worker 领取/续租 → 报告模型 → 租约校验写入 → ResultPage。

## 最值得理解的设计

- **状态控制在服务端。** 场景快照避免训练途中被场景编辑改变；revision 与轮次检查约束并发。新 Runtime 默认开启，但仍可回退 legacy 对话编排，因此阅读旧注释时需要核对运行分支。
- **三个模型职责分开。** NPC 负责买方台词；评分负责情绪与建议；独立评估器负责完成判断。这意味着新路径不能再按旧文件注释理解为“每轮固定两次 LLM 调用”。无工具且存在目标时通常涉及三类调用，工具、失败重试和策略短路会改变次数。
- **记忆保存证据而非自由改写结论。** 事实含消息来源与说话者；截断时记录省略量。上下文默认预算 16000 使用 UTF-8 字节保守估算，不是供应商 tokenizer 实测 Token 数。
- **复盘任务可恢复。** SQLite 的 `jobs`、唯一键、租约、心跳和提交令牌让后台线程失效后可以接管。报告生成不长时间占用业务写事务。当前默认 Worker 在 API 生命周期启动，也提供独立运行入口；Compose 没有单独 Worker 服务。
- **语音适配保留旧契约。** `/polly/convert`、Kazuha 和 PollyService 命名仍在，但当前合成为 edge-tts。中文 viseme 由词边界和码位取模近似生成，不应理解为精准音素口型。

## 当前边界与后续重点

1. **模型质量验收仍未完成。** 2026-09-05 的仓库记录报告 107 项后端测试和 10 组离线契约通过；自然对话首批自动检查为 4/5，失败例后续单独复测通过，但仍观察到证据失配和重复预算导致进度上升。这些是历史小样本记录，本次没有重跑，不能作为当前生产准确率。
2. **知识能力目前很窄。** 四个工具中的知识检索只有两条版本化本地训练规则；企业资料检索、长期能力画像和完整训练推荐仍待建设。
3. **录音文件复盘未接通。** 本地 AudioAnalysisPage 暂不接受上传；不要从旧 AWS 页面或服务方法推断能力已完成。
4. **前端仍有迁移残留。** 大型 ConversationPage 与 ApiService 同时包含多种责任和旧命名；README 声称 Vite 7，而 package.json 已为 Vite 8。后续维护可优先明确契约并拆分语音、状态恢复、会话结束和复盘逻辑。
5. **容量没有实测依据。** 单库 WAL 与默认进程内 Worker 是当前部署形态，不能据此推算高并发容量。应先测完整一轮延迟、ASR CPU 占用、数据库写竞争与复盘积压，再决定是否拆分资源。
