# 销练多多 Agent Harness 改进方案

> 文档版本：v1.0  
> 编制日期：2026-09-05  
> 适用范围：`server/` 本地化后端、`frontend/` Web 前端及后续生产部署  
> 参考基线：`agent-blueprint/BLUEPRINT.md`

## 1. 执行摘要

销练多多当前是一套由固定 AI 工作流驱动的销售陪练产品：用户每输入一轮内容，后端并行调用“模拟客户”和“实时评分”两个模型，保存对话、情绪及目标状态；训练结束后，再异步调用复盘模型生成报告。

当前系统已经具备轻量领域 Harness 的基础，包括：

- 系统提示词与角色约束；
- 会话历史、情绪指标和训练目标状态；
- 多模型角色分工；
- 模型超时、重试与结构化输出解析；
- 会话、消息、评分和报告持久化；
- JWT 身份认证与部分业务权限；
- 基础日志和模型调用轨迹。

但按照 Agent Harness 的严格定义，当前仍属于“程序决定流程、模型负责生成”的固定工作流，不具备“模型选择工具 → Harness 校验并执行 → 返回观察结果 → 模型继续决策”的 Agent Loop。

本方案不把销练多多改造成通用 Agent 开发平台，而是将其演进为：

> **面向销售训练场景的领域专用 Agent Harness。**

核心目标是提升陪练的上下文连续性、角色稳定性、复盘可靠性、个性化训练能力和生产环境可治理性，而不是为了技术完整度堆叠所有 Agent 组件。

## 2. 当前架构判断

### 2.1 当前运行链路

```text
用户语音或文字输入
  → React 前端
  → FastAPI 会话接口
  → 读取场景、NPC、历史消息、情绪和目标
  → 并行执行：NPC 回复模型 + 实时评分模型
  → 解析评分并保存消息、指标、目标状态
  → 返回前端并进行 TTS 播放
  → 用户手动结束或达到轮次上限
  → 后台线程生成复盘报告
  → SQLite 保存报告
  → 前端展示陪练复盘
```

### 2.2 当前产品定位

| 判断维度 | 当前结论 |
|---|---|
| 是否是 AI 产品 | 是 |
| 是否有多个模型角色 | 是：NPC、实时评分、复盘、场景生成 |
| 是否有 Agent 式状态 | 部分具备：情绪、目标、会话历史 |
| 是否有固定 AI 工作流 | 是 |
| 是否有模型自主工具调用 | 否 |
| 是否有完整 Agent Loop | 否 |
| 是否是通用 Agent Harness 平台 | 否，也没有必要成为通用平台 |
| 最合适的演进方向 | 领域专用 Agent Harness |

### 2.3 已知主要缺口

1. 模型不能自主选择领域工具，所有执行路径由代码写死。
2. 对话只截取最近若干条消息，没有会话摘要和 Token 预算管理。
3. 没有跨场次用户记忆，无法形成持续更新的能力画像。
4. 复盘使用进程内后台线程，服务重启后可能卡在 `processing`。
5. 本地 Guardrail 目前是占位实现，安全主要依赖提示词。
6. 缺少统一的调用 Hooks、策略管道和工具审计。
7. 缺少针对角色一致性、重复回复和目标判断的自动化 AI 质量回归。
8. 有基础日志与轨迹，但缺少完整 Trace、成本、质量指标和隐私治理。
9. 本地版本没有知识库检索、来源引用和产品资料事实核验。
10. 旧 `cdk/` 中的 AWS/Strands 实现已经不是当前生产运行路径，容易造成架构认知混乱。

## 3. 改进目标与非目标

### 3.1 总体目标

在不破坏现有前端接口和训练流程的前提下，建立可测试、可恢复、可观测、可扩展的领域 Agent 运行底座。

一次完整闭环应达到：

```text
选择训练场景
  → Agent 获取场景和学员历史能力画像
  → 进行连续、角色稳定的客户模拟
  → 每轮提取客户需求、异议、承诺和目标进展
  → 根据状态动态调整客户策略与训练难度
  → 判断训练是否完成或需要用户继续
  → 生成有事实依据的复盘
  → 写入用户能力画像和下一次训练建议
```

### 3.2 非目标

现阶段不优先建设：

- 通用 Shell、文件系统或浏览器操作 Agent；
- 多 Agent 团队和复杂任务认领系统；
- 面向第三方开发者的通用 Agent SDK；
- 无明确业务需求的 Cron 自治任务；
- 为了匹配蓝图而照搬全部 17 个组件。

这些能力只有在出现明确产品需求时再加入。

## 4. 目标分层架构

| 层级 | 当前实现 | 目标实现 |
|---|---|---|
| 交互层 | React、文字、麦克风、TTS、3D/卡通角色 | 保持现有体验，增加流式状态、错误恢复和训练阶段提示 |
| 产品层 | 场景、会话、历史、复盘、邀请登录 | 增加训练计划、能力画像、知识资料和管理员质量看板 |
| Agent 编排层 | 固定 Python 函数并行调用模型 | 建立领域 Runtime、工具池、Policy、Hooks、Context、Goal Evaluator |
| 模型层 | DeepSeek chat/reasoner | 增加模型路由、结构化输出、降级模型、调用预算和熔断 |
| 能力集成层 | SQLite、ASR、TTS、场景接口 | 将知识检索、会话状态和报告能力注册为领域工具；预留 MCP 适配器 |
| 数据层 | 用户、场景、会话、消息、报告 | 增加会话摘要、事实、用户能力画像、任务、工具审计和运行轨迹 |
| 基础设施层 | FastAPI、SQLite、进程内线程、Docker Compose | 增加持久任务队列、Worker、健康检查、备份、指标和生产配置检查 |

  ├─ Domain Agent Loop
  │    ├─ NPC Agent

## 5. Harness 组件选型

### 5.1 必须建设

| 组件 | 选择原因 | 实现边界 |
|---|---|---|
| 领域 Runtime | 统一目前分散的提示词、模型调用、评分和状态更新 | 不做通用 Agent SDK |
| 领域工具系统 | 让模型按需获取知识、记录事实和更新目标 | 只开放销售陪练相关工具 |
| Policy 与 Hooks | 安全、校验、审计和监控需要统一入口 | 不允许模型绕过业务权限 |
| 上下文管理 | 解决长对话遗忘、重复和 Token 浪费 | 最近消息 + 事实状态 + 动态摘要 |
| 会话内记忆 | 持久化需求、异议、预算、决策链和承诺 | 结构化事实优先于自由文本摘要 |
| 跨场次能力画像 | 支撑个性化训练和长期成长 | 只保存与训练有关的能力信息 |
| 目标闭环 | 可靠判断继续、完成、失败或需要澄清 | 使用独立 Evaluator，不让 NPC 自评 |
| 持久工作流 | 解决复盘、音频分析在重启后的恢复问题 | 至少一次执行，业务侧幂等 |
| 可观测性 | 支撑质量、成本和故障治理 | 默认脱敏，不记录密钥和完整敏感信息 |
| AI 质量评测 | 防止提示词和模型升级导致效果回退 | 固定样例 + 自动评分 + 人工抽检 |

### 5.2 条件性建设

| 组件 | 触发条件 |
|---|---|
| Skill 加载 | 行业、产品或销售方法论资料明显增多，单个提示词难以维护 |
| MCP 适配 | 需要连接 CRM、企业知识库、日历或培训系统 |
| 子 Agent | 场景生成、事实核验、复盘等任务需要隔离上下文或并行处理 |
| 定时调度 | 上线定期训练提醒、周报、团队训练任务后再加入 |
| 多 Agent 团队 | 出现复杂异步研究、批量内容生成或企业级运营需求后再评估 |

## 6. 建议代码结构

在现有 `server/app/` 内增量建设，不重写整个项目：

```text
server/app/
  harness/
    runtime.py              # 单轮 Agent Runtime 与状态流转
    state.py                # PracticeState 类型和序列化
    context.py              # 最近消息、事实、摘要、能力画像组装
    model_router.py         # 模型选择、预算、fallback、熔断
    policy.py               # 权限、安全和副作用策略
    hooks.py                # 调用前后、工具前后统一扩展点
    observability.py        # trace、token、成本、质量事件
    tools/
      registry.py           # 工具 schema、handler 和副作用等级
      scenario.py           # 场景读取
      knowledge.py          # 产品资料与销售知识检索
      session.py            # 会话事实、情绪、目标更新
      learner.py            # 学员能力画像读写
      review.py             # 复盘任务触发与状态查询
    evaluators/
      scoring.py            # 实时评分
      goal_completion.py    # 结束条件判断
      safety.py             # 输入输出安全检查
      regression.py         # 离线质量评测
  workflows/
    review.py               # 可恢复复盘流程
    audio_review.py         # 可恢复录音转写与分析流程
  workers/
    jobs.py                 # 持久任务消费与重试
```

现有接口、前端类型和数据表先保持兼容，通过适配层逐步把逻辑迁入 `harness/`。

## 7. 领域工具设计

第一版只建设必要工具，避免工具过多导致延迟和不确定性增加。

| 工具 | 用途 | 副作用 | 权限 |
|---|---|---:|---|
| `get_scenario_context` | 获取场景、NPC、目标和初始状态 | 无 | 当前用户可读场景 |
| `get_session_state` | 获取会话摘要、事实、指标和目标进展 | 无 | 仅会话所有者 |
| `retrieve_sales_knowledge` | 检索产品资料、话术和合规规则 | 无 | 按资料可见范围 |
| `record_customer_fact` | 记录预算、需求、异议、决策人等事实 | 有 | 仅当前会话 |
| `update_goal_status` | 更新训练目标证据和进度 | 有 | Evaluator 专用 |
| `update_customer_state` | 更新信任、愤怒和谈判进度 | 有 | Evaluator 专用 |
| `get_learner_profile` | 读取历史能力画像和待改进项 | 无 | 仅本人或授权教练 |
| `enqueue_review` | 创建可恢复复盘任务 | 有 | 仅当前会话所有者 |
| `complete_practice` | 完成训练并冻结本场状态 | 有 | 需要满足结束规则或用户确认 |

工具执行规则：

1. 工具参数必须通过严格 schema 校验。
2. 模型不能直接执行 SQL，只能调用受控 handler。
3. 写操作必须校验用户、会话和资源归属。
4. 评分工具与 NPC 工具使用不同权限，NPC 不能自行修改评分。
5. 每次工具调用记录 trace、输入摘要、结果、耗时和错误。
6. 外部资料和工具描述不能自行扩大权限。

## 8. 状态、上下文与记忆

### 8.1 PracticeState

建议建立统一的领域状态对象：

```json
{
  "sessionId": "...",
  "scenarioId": "...",
  "turn": 6,
  "stage": "needs_discovery",
  "customerState": {
    "anger": 2,
    "trust": 5,
    "progress": 4
  },
  "facts": [
    {
      "type": "budget",
      "value": "每月可投入 3000 元",
      "evidenceMessageId": "...",
      "confidence": 0.94
    }
  ],
  "objections": [],
  "commitments": [],
  "goalStatuses": [],
  "summary": "..."
}
```

### 8.2 上下文组装顺序

每轮模型上下文按以下优先级组装：

1. 不可变系统规则和安全边界；
2. NPC 身份、场景和本轮训练目标；
3. 已确认的结构化事实、异议和承诺；
4. 当前情绪、谈判阶段和目标状态；
5. 会话摘要；
6. 最近原始消息；
7. 与当前问题相关的知识检索结果。

不再单纯依赖固定“最近 10 条消息”。当 Token 接近预算时，优先保留规则、结构化事实和最近对话，压缩较早原始消息。

### 8.3 跨场次能力画像

建议按用户维护以下能力：

- 需求挖掘；
- 倾听与复述；
- 价值呈现；
- 异议处理；
- 合规表达；
- 推进与成交；
- 产品知识；
- 表达清晰度。

画像更新必须附带场次和证据，不能只保存模型的一句主观判断。

## 9. 工作流与后台任务改造

### 9.1 当前问题

复盘任务使用进程内 daemon thread。若服务在生成过程中退出：

- 线程直接丢失；
- 数据库可能永久保留 `processing`；
- 用户只能看到持续生成中；
- 无法确认任务执行到哪一步。

### 9.2 第一阶段实现

独立开发阶段可先使用 SQLite Job 表 + Worker，不必立即引入复杂中间件。

```text
jobs
  id
  type
  resource_id
  payload_json
  status           pending/running/completed/failed/dead
  attempt
  max_attempts
  locked_at
  heartbeat_at
  next_run_at
  error
  created_at
  updated_at
```

要求：

- 创建任务和更新会话状态放在同一事务；
- Worker 原子领取任务；
- 超时的 `running` 任务可重新入队；
- 每一步幂等，重复执行不会生成多份报告；
- 支持指数退避和人工重试；
- 服务重启后自动恢复未完成任务。

未来并发量上升后，再替换为 Redis、Celery、Arq 或云队列，业务接口保持不变。

## 10. 安全与权限

### 10.1 必须补齐

- 生产环境未配置安全 JWT Secret 时禁止启动；
- CORS 收敛到明确前端域名；
- 为模型输入和输出增加真实内容安全检查；
- 防止场景资料中的 Prompt Injection 覆盖系统规则；
- 所有资源查询必须校验用户归属和共享范围；
- 工具分为只读、业务写入、敏感外部操作三个副作用等级；
- 错误信息不返回模型密钥、原始堆栈或内部路径；
- 模型轨迹默认脱敏，并配置保存期限和清理策略；
- 音频、转写和对话内容增加用户知情提示与删除入口。

### 10.2 权限边界

```text
NPC Agent
  可读：场景、会话状态、授权知识
  不可写：评分、用户画像、权限

Scoring Evaluator
  可读：对话、目标、场景
  可写：评分、目标证据、客户状态

Review Agent
  可读：已完成场次的完整数据
  可写：本场复盘和画像更新建议

Application Service
  最终负责：身份验证、数据库事务、任务状态和权限裁决
```

## 11. 可观测性与评测

### 11.1 在线可观测性

每一次用户输入生成统一 `trace_id`，串联：

- HTTP 请求；
- 上下文组装；
- 模型调用；
- 工具调用；
- 评分解析；
- 数据库提交；
- TTS/ASR；
- 复盘任务。

建议记录：

- 请求成功率和错误类型；
- 首次响应与完整响应延迟；
- 输入/输出 Token 和单轮成本；
- 模型重试、fallback 和结构解析失败；
- 工具调用次数、耗时和失败率；
- 复盘队列等待时间及最终成功率；
- ASR 无结果率和用户手动修改率。

### 11.2 离线 AI 质量评测

建立固定测试集，至少覆盖：

1. 正常需求挖掘；
2. 用户表达模糊；
3. 语音转写噪声；
4. 连续重复提问；
5. 强烈客户异议；
6. 合规红线；
7. 用户试图改变 NPC 身份；
8. 长对话中的早期事实承接；
9. 目标达成与未达成边界；
10. 模型超时、错误 JSON 和后台任务重启。

核心指标：

- 角色一致性；
- 上下文事实正确率；
- 重复回复率；
- 目标判断准确率；
- 评分稳定性；
- 建议的可执行性；
- 安全违规率；
- 完整流程成功率；
- 延迟和成本。

## 12. 分阶段实施计划

### 阶段 A：生产可靠性基线

建议周期：5～8 个独立开发人日。

任务：

- 将复盘线程改为 SQLite Job + Worker；
- 增加任务超时恢复、重试和幂等；
- 增加生产配置启动检查；
- 收敛 CORS；
- 建立 trace_id、模型调用指标和脱敏日志；
- 建立 10 组核心对话回归样例；
- 修复录音复盘本地链路或暂时明确下线未实现入口。

验收：

- 服务在复盘过程中重启，任务能够自动继续；
- 不会出现永久 `processing`；
- 所有模型调用可按 trace 查询；
- 核心回归样例可以一条命令执行；
- 生产危险默认配置会阻止启动。

### 阶段 B：上下文与状态 Harness

建议周期：6～10 个独立开发人日。

任务：

- 建立 `PracticeState`；
- 提取需求、异议、预算、决策人和承诺等结构化事实；
- 增加动态会话摘要；
- 用 Token 预算替代固定消息条数；
- 将 NPC、评分和目标状态统一接入 Runtime；
- 引入独立目标完成 Evaluator。

验收：

- 长对话能正确引用早期已确认事实；
- 摘要不会覆盖系统规则和结构化事实；
- NPC、评分和目标状态使用同一份权威状态；
- 达成目标、达到上限和用户手动结束均有明确结束原因。

### 阶段 C：领域工具与安全管道

建议周期：6～10 个独立开发人日。

任务：

- 建立工具注册表和 JSON Schema；
- 实现第一批领域工具；
- 增加 PreToolUse/PostToolUse Hooks；
- 增加工具副作用等级、权限检查和审计；
- 增加输入、检索内容和输出安全策略；
- 保持现有 API 契约，通过适配层逐步切换。

验收：

- 模型能按需读取知识和记录会话事实；
- 未授权工具调用默认拒绝；
- NPC 无法修改评分或越权读取其他用户数据；
- 所有工具调用均有审计记录；
- 关闭新 Runtime 后可回退到旧固定链路。

### 阶段 D：个性化与知识增强

建议周期：5～8 个独立开发人日。

任务：

- 建立用户能力画像和证据模型；
- 将复盘结果转化为下一场训练建议；
- 增加产品资料与销售方法论检索；
- 为知识结果保存来源与版本；
- 根据用户弱项推荐下一场景和难度。

验收：

- 用户可看到能力随场次变化；
- 每个能力结论可以追溯到具体训练证据；
- 对产品事实的回答可以展示来源；
- 下一场训练推荐能够解释原因。

### 阶段 E：可选扩展

按真实需求选择，不纳入当前完成标准：

- CRM、企业知识库 MCP 接入；
- 行业 Skill 按需加载；
- 场景生成与资料核验子 Agent；
- 团队训练任务、周报和定时提醒；
- PostgreSQL、Redis/云队列和水平扩展。

## 13. 建议数据模型增量

| 表 | 用途 |
|---|---|
| `session_states` | 当前会话的权威 PracticeState |
| `session_facts` | 带来源消息和置信度的结构化事实 |
| `session_summaries` | 分阶段会话摘要及覆盖范围 |
| `learner_profiles` | 用户能力画像当前快照 |
| `learner_evidence` | 能力变化对应的场次和对话证据 |
| `knowledge_documents` | 产品和销售知识资料元数据 |
| `knowledge_chunks` | 可检索知识片段和来源 |
| `jobs` | 可恢复后台任务 |
| `tool_audits` | 工具调用、权限决策和执行结果 |
| `agent_traces` | 一轮完整 Agent 运行的可观测记录 |

第一阶段仍可使用 SQLite；当出现多人并发、多个 Worker 或高频写入时，再迁移 PostgreSQL。

## 14. 建议验收指标

以下为建议目标，实施前应先采集当前基线，再确定最终阈值。

| 维度 | 建议目标 |
|---|---|
| 核心流程完整成功率 | 连续 10 场不少于 90%，稳定后提升至 98% |
| 复盘最终成功率 | 自动重试后不少于 99% |
| 后台任务恢复 | 服务重启后未完成任务 100% 可恢复或明确失败 |
| 角色一致性 | 固定评测集中不少于 95% |
| 上下文事实正确率 | 不少于 95% |
| 明显重复回复率 | 低于 5% |
| 越权访问 | 自动化测试中为 0 |
| 工具审计覆盖率 | 有副作用工具为 100% |
| Trace 覆盖率 | 模型和工具调用为 100% |
| 敏感轨迹 | 默认脱敏，密钥泄露为 0 |
| 成本 | 建立单轮、单场、单份复盘成本基线与预算告警 |

## 15. 风险与控制策略

| 风险 | 控制策略 |
|---|---|
| 工具调用增加延迟 | NPC 主回复保持最短路径，只在必要时调用只读工具 |
| Agent 自主性导致行为不稳定 | 状态和评分由 Application/Evaluator 掌权，NPC 权限最小化 |
| 新旧链路同时存在造成复杂度 | 使用 Feature Flag，每个阶段完成后删除对应旧实现 |
| 摘要遗漏关键事实 | 结构化事实优先，摘要只压缩叙事，不覆盖证据 |
| 长期记忆保存错误结论 | 每条画像变化必须绑定来源场次和置信度 |
| 模型升级造成质量回退 | 固定评测集、版本化提示词和灰度开关 |
| 轨迹数据涉及隐私 | 脱敏、最小采集、保存期限和用户删除能力 |
| SQLite 达到并发瓶颈 | 保持 Repository 接口，后续平滑替换 PostgreSQL |

## 16. Definition of Done

当以下条件全部满足时，可以认为销练多多第一版领域 Agent Harness 已完成：

1. 存在统一的 Agent Runtime，而不是由路由直接拼接所有模型调用。
2. 至少一组领域工具由模型按需选择，并经过 schema、权限和审计管道。
3. NPC、评分和目标判断使用同一份权威 PracticeState。
4. 长对话具备结构化事实和动态摘要，不再只截取固定消息数。
5. 用户具备跨场次、可追溯证据的能力画像。
6. 复盘和录音分析任务在服务重启后可以恢复。
7. 有真实内容安全策略，而不是仅靠提示词或占位 Guardrail。
8. 每轮模型、工具和工作流都有统一 Trace、延迟、Token、成本与错误记录。
9. 固定 AI 质量回归集进入日常测试流程。
10. 新 Runtime 可以通过 Feature Flag 回退，且现有前端接口保持兼容。

---

## 17. 独立开发者推荐执行顺序

最合适的顺序不是先写通用 Agent Loop，而是：

```text
第一步：可恢复复盘任务 + Trace + 评测集
第二步：PracticeState + 结构化事实 + 动态摘要
第三步：领域工具注册表 + Policy + Hooks
第四步：长期能力画像 + 知识检索
第五步：根据真实客户需求决定 MCP、Skill、子 Agent 和定时任务
```

该顺序可以确保每一步都直接改善产品体验，同时避免一次性重构带来的高风险。

## 18. 对外技术表述

改造前：

> 销练多多是一套由多角色大模型驱动的状态化销售陪练系统，通过客户模拟、实时评分和复盘分析组成完整训练闭环。

完成阶段 C 后：

> 销练多多基于领域专用 Agent Harness 构建，通过受控工具、会话状态、长期能力记忆、目标评估和可恢复工作流，为销售人员提供连续、可评估、可个性化的 AI 陪练体验。

不建议把产品描述为“通用 Agent Harness 平台”，因为产品真正的差异化价值是销售训练闭环、场景知识、评测体系和用户能力成长，而不是通用 Agent 基础设施。
